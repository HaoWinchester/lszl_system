# P4.5.29 服务器整合——业务功能转移清单

## 一句话目标

不是把服务器版替换成本地版，而是把 **P4.5.29 的内容生产与学习业务能力** 接入现有服务器的 **多人协作、版本记录、权限、API 和 Focus/Vega 界面底座**，最终只保留一条主线。

## 业务优先级

- **P0：必须先做。** 不完成会导致最新版 Prep Studio 做出来的题目无法安全进入服务器，或学习端行为不一致。
- **P1：第二批做。** 解决教师后台、多人协作、学习诊断和长期分支维护问题。
- **P2：后续产品化。** 个性化推荐、性能和体验优化。
- **保护：不能被覆盖。** 服务器现有 Catalog、Revision、共享草稿、编辑锁、权限、Paper Quota、Focus/Vega 等能力必须保留。

## 功能转移清单

### B01 · 所有人看到的版本号只保留一套（P0）
- **现在的问题：** 目前服务器包里多个版本号混在一起
- **要做的事情：** 统一到一个正式版本；服务器部署号仅内部使用
- **业务价值：** 避免拿错版本、配错文件、难以回滚
- **主要使用者：** 开发/测试/内容/运维
- **验收方式：** 所有入口显示同一正式版本；发布清单可追溯

### B02 · 单机 Prep 做出来的最新版题目，服务器可以完整接收（P0）
- **现在的问题：** Family、Facet、关键词、原则等新字段可能丢失
- **要做的事情：** 升级服务器导入与保存能力
- **业务价值：** 内容团队不需要再做二次人工修补
- **主要使用者：** 内容/教师
- **验收方式：** 随机抽取完整题导入，字段前后完全一致

### B03 · 题目可以按“母题—成员题”成组管理（P0）
- **现在的问题：** 服务器不认识题目家族
- **要做的事情：** 迁移 Question Family 能力
- **业务价值：** 支持等价训练、能力拆解和高阶验证
- **主要使用者：** 内容/教研/教师
- **验收方式：** 可查看母题关系、成员类型、用途和质量状态

### B04 · 题目分类分成知识点、科目分类、业务标签三套，不再混用（P0）
- **现在的问题：** 服务器分类口径旧且混杂
- **要做的事情：** 迁移 Subject Facets 与新版 Global Tags
- **业务价值：** 筛题、组卷、统计更清晰
- **主要使用者：** 教研/教师/运营
- **验收方式：** 同一道题三类分类都可独立查看和筛选

### B05 · 普通难度和家族层级是两件事（P0）
- **现在的问题：** 旧版本容易把“中等”和 L2 混在一起
- **要做的事情：** 统一新版难度规则
- **业务价值：** 业务沟通不再歧义
- **主要使用者：** 教研/教师
- **验收方式：** 难度只显示简单/中等/困难；L1-L4 只用于家族诊断

### B06 · 关键词必须来自题面，并且知道来自题干还是哪个选项（P0）
- **现在的问题：** 服务器旧逻辑可能串位
- **要做的事情：** 迁移 Keyword v2 和来源隔离规则
- **业务价值：** 减少误判，保证学习端准确点击
- **主要使用者：** 内容/学员
- **验收方式：** 同一个词在题干和选项中可独立存在且互不串位

### B07 · 没有合适联想时可以不绑，不强行凑（P0）
- **现在的问题：** 旧校验容易把空 Recall 当问题
- **要做的事情：** 统一 Recall 可空规则
- **业务价值：** 避免错误联想污染题库
- **主要使用者：** 内容/教研
- **验收方式：** 空 Recall 合法；只有填了不存在的 ID 才报错

### B08 · 录题时可以直接搜索联想入口（P1）
- **现在的问题：** 服务器 Prep 只有下拉框
- **要做的事情：** 迁移模糊搜索
- **业务价值：** 减少查找时间
- **主要使用者：** 内容/教师
- **验收方式：** 可按中英文名、别名、ID 搜索并选择

### B09 · 核心关键词不会提前把答案提示给学员（P0）
- **现在的问题：** 服务器学习端行为未完全对齐
- **要做的事情：** 统一为默认隐藏、点击后揭示
- **业务价值：** 保证练习公平
- **主要使用者：** 学员/教研
- **验收方式：** 普通词和核心词初始视觉完全一致

### B10 · 原则卡文件可以直接导入，不用人工改格式（P0）
- **现在的问题：** 不同版本使用不同原则包格式
- **要做的事情：** 服务器 Prep 支持两种合法格式并自动转换
- **业务价值：** 降低配置门槛和误操作
- **主要使用者：** 内容/教研
- **验收方式：** 两种原则包都可导入并得到相同结果

### B11 · 每个选项可以绑定自己的解题原则（P0）
- **现在的问题：** 服务器已有部分能力但不完整
- **要做的事情：** 补齐选项级原则绑定和正确答案原则汇总
- **业务价值：** 解析、诊断和复盘更准确
- **主要使用者：** 教研/学员
- **验收方式：** A/B/C/D 原则可独立查看；正确答案原则用于总结

### B12 · 删除或更新原则时，不会留下坏引用（P1）
- **现在的问题：** 服务器已有 API 但规则需补齐
- **要做的事情：** 加入引用检查、冲突提示和安全清理
- **业务价值：** 避免题目突然缺配置
- **主要使用者：** 教研/管理员
- **验收方式：** 删除前可看到影响范围；处理后无悬空引用

### B13 · 单机的自动保存体验保留，但服务器仍以共享草稿为准（P1）
- **现在的问题：** 两套持久化方式不同
- **要做的事情：** 把体验迁到服务器 Draft，不搬 IndexedDB 当权威
- **业务价值：** 既好用又能多人协作
- **主要使用者：** 内容/教师
- **验收方式：** 断线/刷新可恢复；多人同时编辑有锁和冲突提示

### B14 · 服务器现有的共享草稿、编辑锁、版本记录不能丢（保护）
- **现在的问题：** 本地版没有同等能力
- **要做的事情：** 作为整合底座完整保留
- **业务价值：** 保护多人协作和可追溯性
- **主要使用者：** 内容/管理员
- **验收方式：** 合并后锁、心跳、Revision、冲突处理全部仍可用

### B15 · 题库、训练配置、试卷管理采用同一套模块化业务规则（P1）
- **现在的问题：** 服务器页面长期独立演进导致分叉
- **要做的事情：** 迁移本地成熟模块边界，但仍走服务器 API
- **业务价值：** 以后功能只改一次，不再双分支
- **主要使用者：** 开发/测试/教师
- **验收方式：** 同一 Domain 能在不同页面复用；无重复实现

### B16 · 训练配置可以真正使用家族、Facet、标签和新版难度（P1）
- **现在的问题：** 服务器训练配置还没接上新题库模型
- **要做的事情：** 升级选题条件和配置
- **业务价值：** 让新元数据产生教学价值
- **主要使用者：** 教师/教研
- **验收方式：** 可按这些字段组合筛选/训练

### B17 · 试卷功能升级时继续保留服务器配额规则（P1）
- **现在的问题：** 本地模块化但服务器有独有 Paper Quota
- **要做的事情：** 融合升级，不直接覆盖
- **业务价值：** 避免组卷业务回退
- **主要使用者：** 教师/管理员
- **验收方式：** 新题库字段可用于试卷，同时配额规则不变

### B18 · 学习系统能基于真实答题证据判断知识点掌握情况（P1）
- **现在的问题：** 服务器缺少新版诊断闭环
- **要做的事情：** 迁移 Evidence/Diagnosis/Decision
- **业务价值：** 提供可信的学习诊断和下一步建议
- **主要使用者：** 学员/教师
- **验收方式：** 证据不足显示“尚未评估”，不硬算分

### B19 · 每次答题保留当时的知识点映射（P1）
- **现在的问题：** 题库后续改映射会影响历史解释
- **要做的事情：** 保存作答时映射快照
- **业务价值：** 历史学习记录可追溯
- **主要使用者：** 教师/学员
- **验收方式：** 旧答题记录不会因后续改题库而改变含义

### B20 · 未来可根据诊断自动推荐最合适的学习内容（P2）
- **现在的问题：** 服务器暂无完整推荐闭环
- **要做的事情：** 后续迁移学习内容与推荐体系
- **业务价值：** 形成个性化学习闭环
- **主要使用者：** 学员/教师
- **验收方式：** 推荐有理由、有完成记录、可评估效果

### B21 · 服务器继续使用现有 Focus/Vega 界面风格（保护）
- **现在的问题：** 本地版有不同 UI
- **要做的事情：** 只迁业务行为，不整套覆盖视觉
- **业务价值：** 降低用户适应成本和前端风险
- **主要使用者：** 学员/教师
- **验收方式：** 新功能在服务器既有视觉体系内工作

### B22 · 服务器账号、权限、题目 ID、版本记录仍由服务器说了算（保护）
- **现在的问题：** 本地版有设备身份、本地 ID/Hash
- **要做的事情：** 不迁移本地权威机制
- **业务价值：** 避免双主数据源和权限漏洞
- **主要使用者：** 管理员/开发
- **验收方式：** 所有正式写操作仍经过服务器身份、RBAC、Revision

### B23 · 每次发布同时检查 Prep、主程序和服务器协作能力（P0）
- **现在的问题：** 过去容易只改一边
- **要做的事情：** 建立联合发布 Gate
- **业务价值：** 防止再次出现“版本一致、功能不一致”
- **主要使用者：** 开发/测试/运维
- **验收方式：** 关键契约、导入、学习端、锁/Revision 回归全部通过才发布

## 建议开发顺序

1. **阶段1：版本与数据契约。** 统一版本、Import Policy、Family、Facet、Global Tags、Difficulty、Keyword v2、Recall、Principle、Deep Recall 最小闭环。
2. **阶段2：教师后台与协作。** 把单机 Prep 的成熟编辑能力和本地主程序的模块边界接到服务器 Shared Draft、Revision、Lock、API。
3. **阶段3：学习端与诊断。** 升级 Recall/Deep Recall，补 Practice 学习事件、知识映射快照、Evidence/Diagnosis/Decision。
4. **阶段4：个性化与优化。** Learning Content、推荐排序、效果归因、Recall 性能和剩余 UX 行为对齐。

## 业务沟通时必须坚持的三条边界

1. **核心关键词不是给学员的提示。** 普通关键词和核心关键词都默认隐藏，点击后才显示。
2. **单机版的本地存储不是服务器正式数据源。** 自动保存体验可以迁，但正式数据仍由服务器权限、Revision 和数据库负责。
3. **服务器现有协作能力不能为了追 P4.5.29 被回退。** 新功能要接入 Catalog/Revision/Shared Draft/Edit Lock/API，而不是替换它们。
