# 多题归纳完成状态、自动个人卡、导入查重与错题掌握设计

## 1. 决策摘要

本轮补齐四条互相关联的学习与录入规则：

1. 多题归纳时，只有所有来源题正确选项共同且唯一绑定同一原则、且该原则存在启用中的系统预设卡，才插入只读系统原则卡；其他情况自动创建数据库个人归纳卡。
2. 学生点击任一选项并由服务器成功保存后，该题立即记为“已完成”，无论正误；答错同时进入错题集。
3. 题目导入按“标准化题干 + 有序选项 + 正确答案”查重，同时检查目标题库和本批内部；发现重复必须让用户确认是否自动清除，再为实际保留题逐题分配稳定编号。
4. 错题是否掌握采用 Update 的延迟验证状态机，不再允许普通做题入口通过一次答对直接把历史错题标记为已掌握。

数据事实均以服务器为准。画布、题目列表和导入弹窗提供即时反馈，但不得在服务器失败时伪造成功状态。

## 2. 多题归纳卡判定

### 2.1 系统卡条件

对当前选中的至少两道题读取“正确选项绑定的原则 ID”，只有同时满足以下条件才使用系统预设卡：

- 每道题的正确选项都存在有效原则绑定；
- 所有题共同且唯一指向同一个原则 ID；
- 该原则存在状态为 `active` 的系统预设归纳卡。

系统卡保持只读，画布节点记录原则、预设和来源题目引用。

### 2.2 个人卡回退

以下任一情况都不再阻断归纳，而是创建个人卡：

- 有题未绑定原则；
- 不同题绑定不同原则；
- 共同原则不唯一；
- 原则存在但没有启用中的系统预设卡。

创建顺序必须是：先调用个人归纳卡 API 创建数据库记录，再把带 `personalCardId` 的引用插入画布并建立来源题支持关系。默认标题为 `我的归纳（N 题）`，正文为空，来源题稳定引用完整保存；创建成功后进入现有个人卡编辑流程，学生可立即补充标题和内容。

API 失败时不创建只存在于画布的孤儿卡，保留题目选择并显示可重试错误。

## 3. 题目完成状态与作答

### 3.1 完成判定

“已完成”只表示学生已经成功提交过一个选项，不代表答对或掌握：

- 点击选项后先调用统一服务器判题接口；
- 接口成功返回后，以题目、题库、试卷和发布版本的稳定上下文写入学习会话 `completed`；
- 左侧题目行立即重新渲染为“已完成”，并同步更新“全部/未完成/已完成”筛选；
- 后续重复作答不改变首次完成事实，但仍可更新错题状态；
- 网络或服务器失败时不写完成状态，保留选择和重试入口。

### 3.2 正误与错题

- 答错：服务端 upsert 当前发布版本的错题记录，并返回最新错题状态；前端刷新错题集数量。
- 答对且从未答错：不创建错题记录。
- 答对且已有错题：按第 5 节状态机推进，不直接移出错题历史。

完成状态与错题状态分别持久化，互不覆盖。

## 4. 导入查重与逐题编号

### 4.1 规范签名

为每题计算统一内容签名，字段为：

```text
canonical(primary stem)
+ ordered canonical(option id, option text)
+ canonical(correct answer)
```

规范化规则：Unicode NFKC、去首尾空白、连续空白折叠、英文字母大小写归一；保留标点和选项顺序，避免把语义不同题误判为重复。题干优先使用中文主内容，缺失时回退英文。

签名逻辑在 Content Prep 和题库管理导入入口共享同一契约，并由服务端批量导入再次校验，避免并发或旧页面绕过。

### 4.2 预检与确认

导入前同时比较：

- 目标题库现有题目；
- 本次导入批次中较早出现的题目。

发现重复后展示已有重复数、本批重复数和将保留的题目数，并询问是否自动清除：

- 确认：现有题目始终保留；本批相同签名只保留第一次出现；随后一次性提交剩余题目。
- 取消：整批不导入，不修改题库，不消耗编号。
- 无重复：直接导入。

### 4.3 编号

只对去重后实际写入的题目分配编号。每题一个稳定 `teacherNumber`，同一编号不能供多题共用；被清除、失败或回滚的题目不应在成功结果中占用编号。批量写入必须是原子操作，不能出现只导入一部分却显示整体成功。

## 5. 错题掌握状态机

### 5.1 状态与转换

采用 Update 的保守判定：

```text
首次答错 -> pending
pending 后首次答对 -> verification_due（nextReviewAt = 当前时间 + 24h）
复仇作答再次答错 -> needs_remediation
完成补救并答对不同验证题 -> verification_due（重新等待 24h）
到期后再次答对原错题 -> mastered
mastered 后再次答错 -> pending（重新激活）
```

`needs_remediation` 不能通过普通画布把原题点对一次绕过；必须完成已有补救和不同题验证流程。`verification_due` 未到期时再次答对也不提前掌握，只保持等待并返回下一复习时间。

### 5.2 入口一致性

普通练习、多题画布和错题复仇入口必须调用同一服务端状态推进器。客户端只能提交所选答案和来源模式，不能提交可信的 `correct`、`mastered` 或目标状态。

默认错题集展示 `pending`、`needs_remediation` 以及已经到期的 `verification_due`；未到期验证项显示“等待复习”和具体时间；`mastered` 只在已掌握筛选中展示。

本轮不引入 Update 中知识点综合分数、证据分或 88 分阈值；那些用于更高层的知识诊断，不等同于单道错题是否掌握。

## 6. 权限、失败与恢复

- 完成记录、个人卡和错题均按当前登录学生隔离，服务端忽略客户端 owner。
- 教师题库导入需要现有题库编辑权限；查重结果不得泄露无权访问题库的内容。
- 创建个人卡、提交答案或导入失败时，前端保留可恢复输入，不展示成功状态。
- 重复提交作答采用幂等完成写入；重复导入提交由签名校验和事务再次阻止重复。
- 个人卡仍使用 revision 乐观并发；本轮不改变已有冲突规则。

## 7. 验收标准

### 7.1 多题归纳

- 两道题正确选项绑定同一原则且存在启用预设：得到只读系统卡。
- 缺绑定、不同绑定、多个共同原则或无启用预设：得到一张数据库个人卡并进入编辑；刷新和其他画布仍可在“我的归纳卡”看到。
- 个人卡 API 失败：画布不产生孤儿节点，可原选择重试。

### 7.2 完成与错题

- 答对或答错任一题，服务器保存成功后左侧立即变“已完成”。
- 答错后错题集数量和列表即时更新；提交失败不完成、不伪造入集。
- 刷新、重新登录和切换画布后完成状态仍存在。

### 7.3 导入

- 已有重复、本批重复和混合重复均能准确统计并弹出确认。
- 取消后数据库零变化；确认后只写唯一题目，保留批次第一次出现。
- 题干相同但选项或正确答案不同不作为完全重复。
- 去重后每道题都有不同稳定编号。

### 7.4 掌握

- 历史错题第一次答对只进入待验证，不立即 mastered。
- 未到 24 小时不能提前掌握；到期后再次答对才能掌握。
- 补救状态不能由普通画布绕过；已掌握后答错可重新激活。

## 8. 发布约束

- 只修改源代码、后端和正式发布脚本，不手工覆盖 `frontend/public/new-legacy/` 或 active release。
- 发布前比较候选 site 与当前 active site 的有效文件数，候选不得少于当前；抽查 `admin-console.html`、`question-bank.html`、`question-workspace.html` 和 Content Prep 页面。
- 所有相关测试、全量后端测试、前端类型检查和真实浏览器关键路径通过后，才运行 `manage-new-legacy.js update new-legacy --skip-browser` 并部署。

## 9. 自检结论

- 四项规则均有事实来源、正向路径、失败路径、恢复路径和验收标准。
- 明确拆分“已完成”和“已掌握”，消除旧版一次答对直接 mastered 的冲突。
- 查重采用用户确认的完全匹配规则，没有扩展到模糊或 AI 语义查重。
- 无 TBD、TODO 或未决产品问题，可以直接进入实现。
