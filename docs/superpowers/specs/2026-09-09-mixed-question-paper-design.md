## 1. 目标和方案

复用现有题库、组卷、不可变发布、练习会话、成绩、错题和复仇链路，新增混合试卷能力。

方案比较：

1. **推荐：新增混合试卷类型，扩展公共题目与答案契约。** 新建试卷默认提供“混合试卷”，可编排单选、多选、图表、匹配、案例；保留现有普通和多选专项试卷规则及历史发布内容。可以明确校验新能力，避免旧试卷的类型约束被静默改变。
2. 扩大现有普通试卷的含义，使普通试卷直接接受所有新题型。入口较少，但会改变现有普通试卷与多选专项试卷的明确边界，历史客户端也可能误按单选处理。
3. 为三类新题另建答题系统。会重复实现组卷、会话、判分和错题，不适合本次扩展。

用户看到五类题目入口；底层区分材料与作答方式。图表是材料，案例是共享材料及题组，作答方式为单选、多选或匹配。首版案例小题支持单选和多选，可附图表；案例内嵌匹配、嵌套案例不列入首版。

## 2. 首版业务规则

### 2.1 图表题

- 教师录入题干、上传图表图片、填写图片说明、选项、答案和解析；选择单选或多选作答。
- 首版使用图片呈现柱状图、折线图、表格等，允许放大查看；不制作在线图表绘制工具。
- 图片纳入系统持久化资源管理及部署备份，发布引用不可变资源版本；不得依赖截图原网站的临时链接。
- 图表既可用于独立题，也可附在案例材料或小题中。
- 图片加载失败时展示明确提示及重试入口，不因资源错误自动提交或判错。

### 2.2 匹配题

- 首版一对一匹配：左侧条目与右侧候选数量相同，至少两对；每个候选只能使用一次。
- 电脑端支持拖拽和点击配对，手机网页及小程序保证点击配对可用。键盘用户可选择条目、候选和取消配对。
- 配对后允许取消、更换；目标已有答案时替换，并把原候选放回候选区。非法或区外放置不改变答案。
- 完成配对后显式提交；部分配对作为草稿保存，离开、刷新、恢复会话后仍可继续。
- 按稳定条目 ID 保存映射；候选顺序变化不能改变答案含义，也不能通过相同的左右 ID 暗示正确关系。
- 全部匹配正确才得该题完整分值；错配、漏配、未提交、超时均为零分。解析逐对显示实际选择与正确关系。
- 暂不支持部分得分、多对一、排序、自由画线或任意拖动物体。

### 2.3 案例题

- 一份案例材料关联多个小题；每个小题有独立 ID、题干、答案、解析和分值。
- 案例材料不单独计题、不单独计分。例如一份案例包含三个小题，在答题卡、进度和总题数中计三题。
- 教师组卷时以案例题组整体加入、移除和移动；小题保持案例内顺序。
- 随机练习按独立题或案例题组打乱，案例小题不拆散。抽题数量按小题计算；无法在整组选取约束下凑足时，返回可用题量和调整提示，由用户调整数量，不静默超额或截断案例。
- 电脑端左侧案例、右侧当前小题；手机端材料在上、小题在下，材料可折叠和展开。切换同案例小题时保留材料阅读位置。
- 每个小题独立提交、判分及记录错题；复习或复仇可以只取错的小题，同时携带该小题对应的完整案例材料。
- 案例不能仅靠相邻题号或标题推断关联；删除仍被引用的材料时拒绝操作并提示引用关系。

### 2.4 端和玩法

- 建议首版范围包含教师网页录入、导入、预览和组卷，以及电脑网页、手机网页、微信小程序作答。
- 普通练习、挑战、学霸、复仇统一按同一题目和判分契约工作，保留现有玩法的计时、生命值和经验规则；计题事件以独立题或案例小题为单位。
- 超时按现有玩法处理未提交答案；候选拖放本身不构成提交，不触发扣血或经验变更。
- 成绩报告同时显示作答方式和材料形式，统计时明确分母，避免图表单选题被重复加入总题数。

## 3. 数据与公共模块

### 3.1 题库与发布

- 在草稿与发布模型、API、导入导出、组卷校验中一致增加混合试卷类型 `mixed`。
- 扩展现有公共题目规范化服务，保留旧 `single_choice`、`multiple_choice` 契约，增加 `matching` 及材料引用、案例归组信息。图表和案例不替代小题原本的作答类型。
- 案例材料需要稳定身份和版本，独立题目引用材料并记录组内次序。实施计划阶段依据现有资源存储和内容修订机制确定最小数据库迁移。
- 发布冻结材料内容、图片版本、题组关系、匹配候选、答案、解析及分值。历史会话和错题只读取对应冻结内容。
- JSON 导入导出覆盖全部新结构；手工编辑覆盖全部首版功能。不把图片 OCR、自动识别国外网站题目或新建文档解析器纳入首版。
- 新材料、候选和配对映射必须参与内容哈希、重复题判断及修订冲突校验，避免被视作未修改内容。

### 3.2 判分、保存和复习

- 在现有 `question_answer_service.py` 建立统一按作答类型分派的校验与判分入口，各路由、会话提交、批量保存和结果生成统一调用。
- 单选和多选请求保持兼容；匹配答案增加结构化映射字段，禁止挤入单个答案字符串。
- 校验映射中的条目是否属于冻结题目、候选是否重复使用、数据是否完整；草稿允许不完整，正式提交要求完整，超时按玩法规则处理。
- 最终成绩由后端计算；前端反馈不能覆盖权威成绩。重复提交、离线重试和并发恢复沿用现有会话修订与幂等约束。
- 扩展网页公共渲染和答题状态模块，由预览、练习、多题工作区、报告和错题页共同调用；小程序采用同一数据契约和对应原生组件。
- 新题型的答案、解析显示遵循既有玩法策略，覆盖新字段，避免只处理旧选择题答案字段。
- 未识别题型明确提示当前客户端不支持并阻止错误作答；不能降级成单选题继续保存。

## 4. 已核查的实现依据

- `backend/app/models/question.py` 与 `backend/app/models/paper_release.py`：试卷类型数据库约束目前仅支持 `standard`、`multiple_choice`。
- `backend/app/schemas/paper.py`：草稿 API 同样限制上述两种类型。
- `backend/app/services/paper_service.py`：普通与多选专项试卷按题型互斥。
- `backend/app/services/question_answer_service.py`：已有选项集合规范化和全对判分入口，适合局部扩展。
- `backend/app/services/practice_session_service.py`：提交、草稿、判分区分单选／多选，随机排序以单题为单位，需要统一扩展。
- `backend/app/models/training.py`：会话答案与运行状态采用 JSONB，已有冻结报告和错题快照。
- `new-legacy/question-studio/question-studio.js`：活动编辑器已有配对编辑与预览，需评估哪些规则可迁入公共模块，不能直接视作正式练习支持。
- `miniprogram/domain/question.ts`：目前非多选类型会被归一为单选，必须修正后才能让混合试卷进入小程序。
- 本次搜索未找到可直接认定为题目图片上传入口的实现；图片存储、鉴权与发布资源访问需要在实施计划前定向核查，不能假定已有能力。
- 当前功能分支及工作区有大量既有修改，涉及本功能依赖的会话、练习页、小程序模块。实施前审计并选定隔离基础，不重置、覆盖或夹带这些修改。

## 5. 验收与发布

用原创样题构建一张混合试卷：一道普通单选、一道多选、一道图表单选、一道匹配、一个包含三个小题的案例。预期答题卡总计七题。

验收覆盖：

1. 教师创建、编辑、保存、JSON 导入导出、预览、组卷、发布完整往返，材料与答案不丢失。
2. 网页和小程序分别完成混合试卷；案例连续显示，图表可读可放大，匹配可操作和重配。
3. 所有玩法中的正答、错答、超时、未提交、退出恢复、重复提交结果一致。
4. 刷新恢复未提交的匹配草稿；断网恢复与修订冲突不覆盖已经判定的答案。
5. 案例整组随机抽取、数量不足提示、按小题统计正确；错题复习保留图表或案例材料。
6. 修改题库原题和材料后，旧发布、旧会话及历史报告仍展示原版本。
7. 历史单选、多选专项试卷可正常运行；非法匹配映射、跨权限资源引用、未知题型有明确错误。

实施后运行后端现有 pytest、前端同步与设计契约、小程序现有检查及涉及页面的浏览器测试；记录通过、失败和未验证项目。

前端修改落在 `new-legacy/` 或既有适配层；发布使用仓库规定的管理脚本，核对候选与 active release 文件数和关键页面。功能完成后合入、推送并部署 UAT，等待用户业务验收；未获明确验收通过前不合入 main。Git 推送按仓库要求使用当前命令代理并核对远程引用。
