# 全局复仇错题池与逻辑去重设计

## 1. 背景与问题

当前做题大厅按账号统计全部长期错题，但登录用户开始复仇时，服务端只选择当前试卷当前发布版本的错题。因此，其他试卷、旧发布版本以及历史 `release_id` 为空的错题会显示在统计中，却无法进入复仇会话。

本次将复仇模式改为账号级全局错题池，不再依赖大厅当前选中的试卷。同时，同一道题在多个发布版本或历史链路中形成多条错题记录时，只在一次复仇会话中出现一次，但不物理删除原始记录。

## 2. 目标

- 复仇模式支持混合选择不同试卷和不同发布版本的错题。
- `release_id` 为空的历史错题可以进入复仇会话。
- 同一账号下 `question_id` 相同的有效错题在全局复仇池中逻辑合并，只出题一次。
- 保存、恢复、交卷和服务端判题不依赖某一份正式试卷发布。
- 保留原有账号隔离、错题状态机、出题优先级和整卷交卷后才推进长期状态的规则。
- 挑战、学霸和普通练习继续绑定正式试卷及不可变发布版本，不受本次改造影响。

## 3. 非目标

- 不物理删除或改写重复的 `practice_mistakes` 历史记录。
- 不合并不同 `question_id`、仅题干相似的题目。
- 不改变一天后再次验证、需补救和已掌握等状态规则。
- 不在本次改造中重做补救验证交互或经验值公式。

## 4. 方案选择

采用服务端全局快照复仇会话。

不采用虚拟“全局复仇试卷”，因为它会把用户学习状态混入正式试卷发布领域；不采用前端临时拼题，因为保存、恢复和交卷必须由服务端持有权威题目快照。

全局复仇会话不绑定 `paper_id` 和 `release_id`。会话创建时，服务端从长期错题记录中选择并冻结题目快照、错题引用和来源信息。后续读取、保存、恢复、交卷均使用这份服务器冻结快照。

## 5. 全局错题资格与排序

候选记录必须属于当前登录账号，并满足以下状态之一：

- `needs_remediation`；
- `pending`；
- 已到 `next_review_at` 或没有指定复习时间的 `verification_due`。

以下记录不进入当前复仇池：

- 尚未到复习时间的 `verification_due`；
- `mastered`；
- 缺少稳定 `question_id`；
- 冻结快照缺少题干、至少两个有效选项或可判定正确答案。

候选记录先按状态优先级排序：

1. `needs_remediation`
2. `pending`
3. 已到期的 `verification_due`

同状态下依次按复仇答错次数、总答错次数从高到低排序，最后使用稳定记录 ID 保证结果可重复。

## 6. 逻辑去重规则

去重键为当前账号下的 `question_id`。同一 `question_id` 的多条候选记录合并为一个复仇题组，不删除数据库原始记录。

题组代表记录按以下顺序确定：

1. 状态更紧急者优先：`needs_remediation`、`pending`、到期 `verification_due`；
2. `revenge_wrong_count` 更高者优先；
3. `wrong_count` 更高者优先；
4. `updated_at` 更新者优先；
5. 记录 ID 作为稳定兜底。

会话中保留题组包含的全部 `mistakeId`，并指定一个代表 `mistakeId`。题目展示使用代表记录的最新完整 `question_snapshot`。统计展示按去重后的题目数计算可复仇数量，避免页面数字与实际可开卷数量再次不一致。

交卷时只推进代表记录，避免同一次作答重复累计多条历史记录。其他重复历史记录继续保留为审计历史，不参与本次会话状态推进。未来如需永久归并历史记录，应另立数据治理方案。

## 7. 会话数据模型

`practice_sessions.paper_id` 和 `practice_sessions.release_id` 对全局复仇会话允许为空；其他模式仍由服务层强制要求两者非空并校验正式发布访问权限。

全局复仇会话的 `question_order` 每项冻结以下信息：

- `questionId`
- 代表 `mistakeId`
- 重复题组的 `mistakeIds`
- `bankId`
- `orderIndex`
- 来源 `paperId`、`paperName`、`releaseId` 和版本信息
- 服务端权威 `questionSnapshot`
- 用于报告的领域和分值快照

对外会话载荷继续返回现有 `questions` 结构，前端无需从正式发布仓库补题。正确答案仅通过现有受保护会话接口提供给当前账号，用于本地即时判题；客户端不能提交可信的 `correct` 或目标错题状态。

数据库迁移只调整会话外键字段的可空性，不修改现有错题和旧会话内容。

## 8. 创建与恢复规则

前端开始复仇时只提交 `mode=revenge`、题量和固定排序方式，不再提交当前选中试卷的 `paperId/releaseId`。

服务端对同一账号的全局复仇创建使用账号级事务锁，避免重复创建。新全局复仇会话只允许一份活动或暂停进度。

兼容现有单试卷复仇会话：

- 若账号存在旧的活动或暂停复仇会话，优先恢复最近保存的一份，不改写其发布版本和题目来源；
- 旧会话完成或放弃后，下一次开始创建新的全局复仇会话；
- 不自动放弃、不合并仍未完成的旧会话。

大厅“继续上次练习”判断对复仇模式按账号和模式匹配，不再按当前选中试卷匹配。切换试卷不会改变复仇统计、按钮状态或待恢复会话。

## 9. 保存、交卷与状态推进

暂停保存仍只保存草稿答案和运行阶段，不推进长期错题状态。

全局复仇会话的草稿校验、统计、恢复和报告生成统一读取 `question_order` 中的服务器冻结快照。挑战、学霸和普通练习继续读取正式发布题目快照。

整卷交卷时，服务端逐题使用代表 `mistakeId` 对应的长期错题记录和冻结正确答案权威判定：

- 答对 `pending`：进入 `verification_due`，复习时间为一天后；
- 到期的 `verification_due` 再次答对：进入 `mastered`；
- 答错：进入 `needs_remediation`；
- `needs_remediation` 不允许通过普通原题答对绕过补救流程。

任意题判定失败时整卷事务回滚，不产生半份报告或部分错题推进。重复交卷继续返回冻结结果，不重复累计次数。

## 10. 前端行为

- 复仇卡片的待复仇、需补救、到期验证、已掌握统计来自服务端全局去重统计。
- 按钮仅在去重后存在至少一道可用错题或存在可恢复会话时启用。
- 没有候选题时显示明确的全局空状态，不再出现“当前试卷暂无可复仇错题”。
- 历史记录全部缺少可判定快照时，返回具体不可用提示，并允许用户继续使用其他练习模式。
- 切换试卷、试卷下架或发布新版本不影响已创建的全局复仇会话。

## 11. 需求追踪与测试

| 场景 | 预期结果 | 覆盖层 |
| --- | --- | --- |
| 两份试卷各有错题 | 同一复仇会话同时包含两份试卷的题 | API + 浏览器 |
| 历史错题 `release_id` 为空 | 正常进入复仇会话并可交卷 | API |
| 同一 `question_id` 存在多版本记录 | 统计和会话均只出现一次，选择规则稳定 | 服务单元 + API |
| 重复题代表记录作答 | 只推进代表记录一次，其他历史记录不被删除 | API + 数据库断言 |
| 仅有未到期验证或已掌握记录 | 按钮禁用并显示全局无可复仇题 | API + 浏览器 |
| 候选快照损坏 | 跳过损坏项；全部损坏时返回可恢复错误 | 服务单元 + API |
| 用户 A/B 都有错题 | 会话、统计和交卷严格按账号隔离 | API |
| 切换当前试卷 | 复仇数字、按钮和恢复入口保持不变 | 浏览器 |
| 保存后退出并重新登录 | 从冻结快照恢复跨试卷题目及当前阶段 | API + 浏览器 |
| 旧单试卷复仇会话存在 | 优先恢复旧会话，完成后才能创建全局会话 | API + 浏览器 |
| 重复开始或并发开始 | 返回同一可恢复语义，不创建两份全局进度 | API |
| 整卷某题判定失败 | 全事务回滚，可修正后重试 | API |
| 重复交卷 | 返回相同冻结报告且不重复推进错题 | API |

测试遵循先失败后实现。先增加能够复现跨试卷、空版本和重复题目的后端测试，再实现服务端；随后增加前端请求载荷、切换试卷、空状态和恢复入口测试。完成后运行后端全量测试、前端契约测试、定向浏览器测试以及正式发布脚本的内置校验。

## 12. 发布与回滚

后端迁移和代码先在当前数据库副本验证，确认现有非复仇会话仍满足发布版本约束。前端修改只落在 `new-legacy/` 权威源及共享适配层。

正式发布必须通过 `node frontend/scripts/manage-new-legacy.js update new-legacy --skip-browser` 同步、构建、验证并 promote；发布前核对候选站点与 active release 文件数量和关键页面。若上线后需要回滚，前端切回上一 active release，后端字段由非空改为可空属于兼容性扩展，无需破坏性回迁数据。
