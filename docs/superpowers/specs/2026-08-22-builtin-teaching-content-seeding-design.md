# 内置教学基础数据初始化设计

## 背景与目标

当前 `内置数据/` 包含三份 PMP 教学基础数据：

- `PMPv8知识树_可导入包_v8.6.2.json`：PMP 知识树，共 317 个节点；
- `PMP_科目级联想库_PMBOK8_6_V9.json`：科目级联想库，共 471 个节点和 2840 条关系；
- `kg_principle_card_bundle_v1原则卡.json`：8 条原则及其一一对应的 8 张系统归纳卡。

这些数据已有人工导入入口，但环境初始化或数据缺失后，教师需要在创建试卷前重复上传。目标是将三份数据作为项目随附的后端内置资源，由项目文件持续提供规范基线，使教师新建任何试卷时都可以直接使用知识树、联想库、原则和归纳卡。

本功能不修改页面布局、文案、控件或 legacy DOM/CSS。

## 已确认的产品规则

1. 数据写入 PostgreSQL，作为所有管理员和教师共享的教学基础数据。
2. 服务启动时自动检查，不要求用户进入页面或点击导入。
3. 三份项目文件是对应内置记录的规范来源；内置记录缺失时自动恢复，文件内容更新后自动同步到数据库。
4. 自动同步只管理三份文件声明的稳定 ID，不删除或覆盖无关的自定义知识树、联想库、原则或归纳卡。
5. 重复启动必须幂等；文件与数据库一致时不得产生重复记录、无意义修订或重复审计。
6. 后续更新由用户替换项目中的内置 JSON 并重新部署完成，不再通过新建试卷流程上传。
7. 三份内置数据应随代码部署到任何新环境；数据库重建后，下次启动可以重新生成。
8. 新建试卷仍走现有组卷流程和 API，不新增浏览器缓存或前端静态业务数据。
9. 完成本地验证后通过 `deploy/update-uat.sh` 部署测试环境，并实际验证新建试卷可以直接读取内置数据。

## 方案选择

### 采用：后端启动时幂等初始化

将规范化 JSON 放入 `backend/app/seed/`，由独立的内置数据同步服务在数据库连接成功且默认账号初始化完成后执行。服务直接使用当前关系模型写入数据，并对三份文件声明的稳定 ID 执行“缺失则创建、内容变化则更新、完全一致则跳过”。

选择该方案的原因：

- 数据由数据库统一持有，符合现有教学内容关系模型；
- 新环境和数据库重建场景无需人工补步骤；
- 不依赖某位教师登录，也不会按账号重复导入；
- 可以用后端服务测试精确验证幂等、自动恢复和文件升级行为。

### 未采用：部署时运行一次性导入命令

一次性命令无法覆盖后续新环境和数据库重建场景，部署人员仍需记住额外步骤。

### 未采用：前端打开页面后自动导入

这种方式依赖登录角色、页面加载时机和网络状态，会产生重复请求和并发竞态，也会把基础业务数据初始化责任放到浏览器端。

## 数据归属与稳定身份

### PMP 科目

- 稳定科目 ID：`subject-pmp`
- 科目代码：`PMP`
- 若科目不存在则创建；若已存在则复用，不要求覆盖科目自身的展示名称或其他自定义元数据。

### 知识树

- 稳定知识树 ID：使用种子包中的 `taxonomy.id`，当前为 `taxonomy-pmp-complete-v1`。
- 科目 ID：使用种子包中的 `taxonomy.subjectId`，当前为 `subject-pmp`。
- 源版本：使用种子包中的 `taxonomy.version`，当前为 `1`。
- 若相同知识树 ID 已存在，以种子文件同步标题、状态、元数据和全部节点；内容未变化时不写库。
- 若目标 ID 不存在且源版本号未被占用，使用源版本号；若已被其他知识树占用，为内置知识树分配当前科目的下一个可用版本，并在元数据中保留源版本号。
- 不删除同科目的其他知识树版本。

### 科目级联想库

- 归属科目：`subject-pmp`。
- 稳定记录 ID：`recall-subject-pmp-builtin-v1`。
- 源版本：`1`。
- 若稳定 ID 已存在，以种子文件同步 471 个节点、2840 条关系和元数据；内容未变化时不写库。
- 若稳定 ID 不存在且源版本号已被其他联想库占用，分配当前科目的下一个可用版本，并保留其他联想库。
- 状态固定为 `published`，供现有学习和组卷读取链路直接使用。

### 原则与归纳卡

- 使用种子文件中的稳定原则 ID、归纳卡 ID 和原则到归纳卡的一一对应关系。
- 原则 ID 不存在时新增；已存在且内容与文件不同时，同步名称、状态和易混淆关系并递增修订号。
- 每个内置原则同步其对应归纳卡的标题、正文、状态和业务版本；内容未变化时不递增修订号。
- 同一内置原则若已绑定不同 ID 的归纳卡，则将该现有卡同步为文件内容并保留数据库主键，避免破坏一原则一卡唯一约束。
- 归纳卡 ID 若已被另一个原则占用，整次同步失败并回滚，避免错误重绑。
- 不删除文件未声明的自定义原则和归纳卡。

## 组件与职责

### 种子资源目录

在 `backend/app/seed/builtin_teaching_content/` 保存三份经过原样复制的 JSON。目录名称和加载路径使用 ASCII，JSON 内容继续保留中文。

### 种子服务

新增一个职责单一的服务模块，负责：

1. 从固定路径加载三份 JSON；
2. 校验必要版本、ID、节点/关系数组及原则与归纳卡的一一对应关系；
3. 逐类检查数据库已有记录；
4. 对稳定 ID 执行创建、恢复或内容同步；
5. 保留无关的自定义记录；
6. 返回结构化统计，包括 `created`、`updated`、`unchanged` 和警告列表。

同步服务不调用面向人工导入的“全量替换”接口，尤其不调用会删除文件未包含原则的 `import_principle_card_bundle()`。内置数据同步只更新它拥有的稳定 ID。

### 应用启动接入

`backend/app/main.py` 在数据库探活及默认账号初始化后调用种子服务。内置数据初始化失败时：

- 当前种子事务回滚，不留下半套新增数据；
- 记录包含数据类别和错误原因的日志，但不输出环境变量或数据库口令；
- 不把正常数据库错误标记为数据库连接失败，也不阻止应用启动；
- `/api/v1/health` 仍反映数据库真实连接状态。

## 数据流

```text
应用启动
  -> PostgreSQL 探活
  -> 默认账号初始化
  -> 加载并校验三份种子 JSON
  -> 查询共享教学内容关系表
  -> 创建缺失记录或同步已变化的内置记录
  -> 内容完全一致时保持数据库不变
  -> 现有 Content Prep / 组卷 API 读取数据库
  -> 教师新建试卷时直接看到原则、知识树与联想资料
```

前端不直接读取种子 JSON，也不把这些数据写入 `localStorage`、`sessionStorage` 或 IndexedDB。

## 事务与并发

- 单次初始化使用一个数据库事务，校验完成后再执行写入。
- 先获取现有教学内容全局事务锁，再读取版本和稳定 ID，避免多实例同时分配版本。
- 利用现有主键、科目版本唯一约束、原则到归纳卡唯一约束阻止重复记录。
- 只有内容实际变化才递增对象修订号和全局教学内容修订号；完全一致的启动不制造重复审计。
- 任一内置包校验或关系冲突失败时整次事务回滚，不留下半套基线。

| 数据持久化 | 重启、刷新和重新登录后仍从数据库读取 | 不允许浏览器缓存作为业务真源 | 数据库恢复后重新读取 | API/浏览器验收 |

## 测试策略

遵循 TDD，先写失败测试并确认失败原因是种子功能尚不存在，再实现最小代码。

### 后端单元/服务测试

- 校验三份真实种子文件可以被解析，数量分别为 317、471/2840、8/8。
- 空数据库首次初始化后，关系表包含预期稳定 ID 和数量。
- 连续执行两次后数量、修订号和全局内容修订完全不变。
- 删除或修改一个内置稳定 ID 后，重新同步恢复为文件内容。
- 修改测试种子文件内容后，只更新对应内置记录并递增一次修订。
- 文件未声明的自定义知识树、联想库、原则和归纳卡保持不变。
- 同科目版本冲突时为内置记录分配下一可用版本；归纳卡跨原则 ID 冲突时整次回滚。
- 无效 JSON 或跨文件引用不一致时事务回滚。

### API 与用户流程验证

- 以教师身份读取 Content Prep 和试卷配置相关 API，确认返回数据库中的 8 条原则及 PMP 内容引用。
- 新建试卷并选择原则配额，保存后刷新页面，数据仍从后端持久化链路返回。
- 不添加新的上传动作、占位反馈或浏览器持久化。

### 回归验证

- 后端相关测试和完整后端测试套件。
- 前端默认测试、类型/构建检查及相关浏览器测试。
- 已知的既有失败必须单独如实报告，不能把部分通过表述为全绿。

## UAT 部署与验收

1. 将三份种子文件纳入提交，并确认 Docker 构建上下文会复制 `backend/app/seed/`。
2. 发布前核对候选 active release 文件数与当前 UAT active release 对齐，并抽查关键页面存在。
3. 只使用 `bash deploy/update-uat.sh` 部署，禁止手工覆盖 release 或服务器目录。
4. 先通过服务器本机 `127.0.0.1:18087/api/v1/health` 验证服务；公网域名现有 TLS/Nginx 问题不能替代本机健康证据。
5. 核对 UAT 数据库中稳定 ID、节点/关系数量和 8 组原则卡。
6. 使用测试教师账号进入试卷管理，新建试卷、查看原则配额、保存并刷新，确认不再要求上传三份基础数据。
7. 检查部署后日志，无种子校验异常、唯一约束错误或数据库连接错误。

## 非目标

- 不把题库题目或试卷模板加入本次种子；三份文件中本身也不包含题库题目。
- 不修改新建试卷的默认名称、题量、模式、配额或发布策略。
- 不删除现有上传/导入按钮；这些入口仍可用于本次三份内置数据之外的显式版本维护。
- 不为内置记录增加页面内编辑或上传步骤；更新通过替换项目 JSON 并重新部署完成。
- 不删除或覆盖三份文件未声明的自定义教学内容。
- 不在本次工作中处理 UAT 公网域名的 TLS/Nginx 配置问题。
